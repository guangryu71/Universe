# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Starry Sky Universe is a browser-based 3D universe simulator built on Three.js 0.160, plus a small Python standard-library HTTP server for static hosting and SQLite-backed persistence. There is **no bundler, no package.json, and no build step** — the browser loads ES modules directly, and `three` / `three/addons/` are resolved by the import map in [index.html](index.html). That import map points at the jsDelivr CDN, so the app needs network access to load Three.js (vendor it locally if offline work is required). All application code, UI text, and comments are in Chinese.

On top of the simulator it is a **community platform**: cookie-session accounts with four roles (开发者 / 管理员 / 星系指挥官 / 星际公民), galaxy membership, qualitative “new galaxy” offers, a citizen submission review queue, notifications, and developer-only background-music management. All authorization is enforced server-side in `db.py`/`server.py`; the frontend only hides controls.

## Commands

```bash
# Full app (recommended): starts server.py on port 8000, prefers .venv
python start.py            # or start.bat on Windows
# → http://127.0.0.1:8000  (serves the cover page first, click to enter the app)

# Server only (same behavior, no port cleanup / venv detection)
python server.py

# Any static server also works, but the root will not show the cover page
python -m http.server 8000

# Optional Python dependencies (only needed for offline voice synthesis)
pip install -r requirements.txt

# Offline robotic-voice synthesizer (separate from the in-app browser TTS)
python voice_handle/voice.py "你好世界"
python voice_handle/voice.py -p dalek --play "EXTERMINATE!"
python voice_handle/voice.py --list
```

There are **no tests, linters, or build commands** in this repository. Verify changes manually in a browser; the app must be served over HTTP (opening `index.html` via `file://` will fail on ES-module loading).

## Architecture

### Startup flow

`index.html` → import map → [js/main.js](js/main.js) (`SolarSystemApp`, instantiated at the bottom of the file). The constructor wires up every subsystem: `SceneManager`, `PhysicsEngine`, `UIManager`, `SystemManager`, `FocusController`, `GalaxyBrowser`, `ShipModule`, `PlanetLab`, body editor, probe system, time controls, and `_setupCommunity()` (`PersonalCenter`, `AdminPanel` + the two top-right entries). `server.py` rewrites `GET /` to [index_font/heidong.html](index_font/heidong.html), a cover animation that redirects to `index.html` after the intro.

### System/scene model

- [js/scene.js](js/scene.js) owns the renderer, camera, `OrbitControls`, shader starfield, nebula background, and bloom `EffectComposer`.
- [js/SystemManager.js](js/SystemManager.js) keeps **one `THREE.Group` per star system**. Only the active group is attached to the scene; switching hides/removes the old group, unloads its bodies from physics, and loads the new system's bodies. Groups are created lazily once and cached.
- Built-in galaxy modules create meshes into the main scene, then `SystemManager._createSystemScene` re-parents each mesh/ring/glow/label into the system group. Custom galaxies built by `GalaxyBrowser._instantiateGalaxy` add meshes directly into their group.
- **All systems are centered at the origin.** `SYSTEM_POS` is `{0,0,0}` for both built-ins (the docs in `Galaxy-模块标准模板.md` claiming a 30 AU offset for HD 219134 are stale).
- [js/galaxyRegistry.js](js/galaxyRegistry.js) statically imports built-in systems into `SYSTEM_MODULES`. Adding a new built-in system requires: a module under `Galaxy/<id>/index.js`, an import + `SYSTEM_MODULES` entry there, and `systemManager.registerModule(...)` in `main.js`. Custom galaxies are loaded from SQLite (`/api/list-galaxies`), converted to planet-info records by `serverRecordToGalaxy`, cached in `localStorage`, and instantiated by `GalaxyBrowser`; they are never added to `SYSTEM_MODULES`.

### Physics and units

- The physics engine works entirely in **SI units** (kg, m, m/s). [js/constants.js](js/constants.js) holds `G`, `AU`, `POS_SCALE = 22/AU`, `SYSTEM_SCALE = 20`, `SIM_DT`, and `SUBSTEPS`. [js/CelestialBody.js](js/CelestialBody.js) stores `position`/`velocity` in SI and converts to render space as `position × POS_SCALE × SYSTEM_SCALE`; the mesh (not the geometry) is scaled by `SYSTEM_SCALE`, while `realRadius` stays in meters and is used for physics collision clamping.
- [js/physics.js](js/physics.js) is an O(n²) N-body gravity engine using Velocity Verlet with `SUBSTEPS = 4`. Each frame runs `physics.step(SIM_DT * timeScale)` (`SIM_DT = 43200` s ≈ half a day). An optional `physics.onSubstep` callback runs after each substep; PlanetLab uses it for its rigid-sphere collision mode.
- `CelestialBody` subclasses are dynamic bodies in the physics engine. `MoonBody` subclasses are **kinematic** — they are not added to physics and simply orbit their parent mesh. Their static `ORBIT_RADIUS` / `VISUAL_RADIUS` are scene-unit values and the constructor multiplies both by `SYSTEM_SCALE`; `ORBIT_SPEED` is in rad/s.
- Initial orbital velocities come from `setCircularOrbitVelocity(centralMass)`; updated systems should keep this call.

### Galaxy module contract

[Galaxy-模块标准模板.md](Galaxy-模块标准模板.md) is the authoritative module spec and [ADDXINGXI.md](ADDXINGXI.md) is the field/unit reference. Every `Galaxy/<id>/index.js` exports:

- `SYSTEM_INFO` — `{ id, name, nameCN, description, icon }`
- `PLANET_CLASSES` — array of `CelestialBody` subclasses
- `PLANET_DATA` — generated via `_classToInfo` for the registry
- `SYSTEM_POS` — SI-meter offset (currently zero for all systems)
- `MOON_CLASSES` — `{ parentKey: [MoonBodyClass] }` (built-ins)
- `createPlanets(scene, existingPlanets?)` — factory returning `{ key: body }`

Each body lives in its own file as a class with static `KEY`, `NAME`, `NAME_CN`, `MASS`, `RADIUS`, `ORBIT_RADIUS`, `VISUAL_RADIUS`, `COLOR`, `TEXTURE`, `DETAILS`, `VOICE_INTRO`; the constructor calls `super({...})` then `this.position.set(ORBIT_RADIUS, 0, 0)`. `ORBIT_RADIUS` is in meters; `VISUAL_RADIUS` is a scene-unit size. Texture paths are relative to `index.html`.

The `data.json` files inside built-in systems are **not imported by frontend code** — the JS classes are the source of truth. For custom systems, the authoritative record lives in SQLite (`Galaxy/universe.db`); `server.py` also writes an auto-generated `index.js` stub whose `createPlanets` returns `{}` so the folder still looks like a module. `GalaxyBrowser.restoreCustomGalaxies()` first pushes legacy `localStorage` data into the DB, then calls `loadCustomGalaxiesFromServer()` and builds bodies with `_instantiateGalaxy` from the DB records. “再次编译” edits go through `/api/update-galaxy` (same folder/id) and then `SystemManager.refreshActiveSystem`.

Custom systems support an either/or appearance choice per body: **solid color** or **uploaded texture**. `GalaxyBrowser._fileToBase64` downsizes images to ≤512 px and returns a full data URL. On save, `db.materialize_images()` decodes it, writes it under `Galaxy/custom/<id>/media/tex_<sha1>.png`, and replaces the field with that **relative path text** (`texturePath`; `textureData` is set to `null`). The client caches the relative path in `localStorage`, `_toTexturePath` passes it through unchanged, and `CelestialBody` loads it with `TextureLoader`. Both `GalaxyPreview` (live preview) and `ship/js/Hologram.js` (ship hologram) load the same `texturePath`, so the preview, the main scene, and the in-ship projection show the same texture.

### Data storage (SQLite)

[db.py](db.py) is the data layer; [server.py](server.py) is the only writer. The database file is `Galaxy/universe.db` (WAL mode, gitignored user data) and is created/migrated on startup:

| Table | Contents |
| --- | --- |
| `systems` | custom + built-in star systems; the full `data.json`-style record is stored as JSON in `data_json`, `kind` is `custom` or `builtin`. Community columns added by `_ensure_columns`: `owner_user_id`, `universe_galaxy_id`, `status` (`approved`/`pending`/`rejected`), `review_note`, `reviewed_by`, `reviewed_at`, `submitted_at` |
| `universe_galaxies` | universe-level galaxies; the galaxy icon SVG is stored as **text** in `icon_svg`; also `commander_user_id`, `created_by` |
| `body_relations` | directional body-level relations (`from → to`) |
| `detail_files` | detail-compiler entries; `.txt` content is stored inline in `content`, images store only `rel_path` text (`detail_files/...`) |
| `users` | community accounts: `id` is **TEXT** (`u_<hex>`), unique `username`, `display_name`, PBKDF2 `password_hash`, `role` (`developer`/`admin`/`citizen`), `banned` |
| `user_sessions` | hashed session tokens (`token_hash`), `user_id`, `expires_at`; the raw token exists only in the HttpOnly cookie |
| `galaxy_members` | `(galaxy_id, user_id)` membership rows |
| `galaxy_offers` | “新星系资格” published by staff: `quantity`, `remaining`, `created_by`, `active`, icon SVG and detail tree stored as text |
| `offer_claims` | `(offer_id, user_id)` → created `galaxy_id`; uniqueness is what makes claiming atomic |
| `messages` | per-user notifications (`kind`, `title`, `body`, `payload_json`, `is_read`) |
| `meta` | migration flags (`legacy_files_v1`, `legacy_details_v1`, `localstorage_migrated_at`) |

Rules that follow from this:

- **Text data (including SVG) lives in SQLite.** Images never go into the DB: they stay as files and the DB stores a repository-relative path.
- On first startup `db._migrate_legacy()` imports `Galaxy/universes.json`, `Galaxy/body_relations.json`, `Galaxy/custom/*/data.json`, the built-in `data.json` files, and `detail_files/*`. The old JSON files are kept as backups but are no longer read.
- The browser migrates its own `localStorage` once via `POST /api/migrate-local-data` (`universe_custom_galaxies`, `universe_galaxies`, `universe_body_relations`). `loadCustomGalaxiesFromServer()` also re-pushes local-only systems on every boot, so systems created while the server was offline are not lost. `localStorage` is now only an offline cache.
- Record shape in the DB: `star` is a `data.json`-style object (position `x/y/z` in AU), `planets` is a list of the same shape, and `orbitRadius`/`radius` remain SI meters.
- `GET /detail_files/<name>` serves `.txt` rows from the DB `content` column and images from their `rel_path` (falling back to `detail_files/`).
- Community tables are created alongside the legacy ones in the same schema string; new `systems` / `universe_galaxies` columns are added lazily by `_ensure_columns`, so existing databases upgrade in place.

### Community platform (roles, sessions, review)

**Roles and permissions** — always re-checked in `db.py`; the UI hiding a button is not security.

| Capability | 开发者 developer | 管理员 admin | 星系指挥官 commander | 星际公民 citizen |
| --- | --- | --- | --- | --- |
| Appoint/revoke admins, delete accounts | ✅ | — | — | — |
| Ban/unban users (never another admin) | ✅ | ✅ | — | — |
| Review submissions (approve/reject) | ✅ | — | — | — |
| Edit any star system | ✅ | — (delete only) | own systems | own systems |
| Delete any star system | ✅ | ✅ | own systems | own systems |
| Publish “new galaxy qualification” offers | ✅ | ✅ | — | — |
| Appoint/revoke a galaxy's commander | ✅ | — | — | — |
| Delete a universe galaxy | ✅ | — | — | — |
| Edit galaxy info / manage members / kick | ✅ | — | own galaxy | — |
| Background-music management | ✅ | — | — | — |
| Join galaxies, claim offers, post systems | ✅ | ✅ | ✅ | ✅ |

- **Bootstrap**: the first account to register becomes `developer` and takes over all ownerless `kind='custom'` systems plus the default `milky-way` galaxy, which also makes it a member (`register_user`). There is no seeded account and no separate admin login page.
- **Sessions**: `POST /api/auth/register|login` set an HttpOnly `SameSite=Lax` cookie holding the raw token; `user_sessions` stores only its SHA-256 hash. `POST /api/auth/logout` deletes the row. `GET /api/auth/me` returns the public user plus `memberships` and `commandedGalaxies` (derived from `universe_galaxies.commander_user_id`, so a user may command several galaxies). Banned users cannot log in, and banning deletes their sessions. Login failures are throttled in memory by `ip|username`.
- **Passwords**: PBKDF2-SHA256, 8–128 characters; usernames 3–24 characters (`USERNAME_RE`).
- **Review workflow** (citizen posts): `POST /api/create-galaxy` records `status='pending'` for citizens and `'approved'` for staff. Pending posts are **publicly visible** with a 审核中 badge; `rejected` rows are hidden from the public list but still returned to their owner and staff. Editing a citizen-owned system resets it to `pending` and clears the old review note; developer edits stay `approved`. Only `POST /api/review-system` (`developer`) can approve or reject, and it notifies the owner.
- **Drafts**: the compiler footer offers 直接发表 and 暂存到草稿箱; both create/update endpoints accept `draft: true`, which stores `status='draft'`. Drafts are **owner-private** — `list_systems` hides them from everyone else, `GalaxyBrowser`/`UniverseView` never show or instantiate them, and `list_body_relations`/`replace_body_relations` hide (and preserve) relations that touch someone else's draft. `POST /api/publish-system` flips a draft to `pending` (citizen, after a membership check) or `approved` (developer); the owner's 个人中心 → 我的系统 shows a 草稿 badge and a 🚀 完成发布 button that calls `GalaxyBrowser.publishDraft()`. The lab's 导出星体数据库 → 保存至草稿箱 uses the same path through `GalaxyBrowser.addSystemFromLab({ ..., galaxyId, draft: true })`, which forwards `draft` to `createGalaxyOnServer` and deliberately does **not** instantiate the bodies into the main scene while the system is a draft.
- **Membership**: citizens must join a galaxy before posting into it (`POST /api/galaxy/join|leave`). Leaving a galaxy you command is refused. `POST /api/galaxy/kick` requires the commander of that galaxy or the developer, and notifies the kicked user. `POST /api/galaxy/members` lists members.
- **Offers**: staff publish a `galaxy_offers` row with `quantity`/`remaining`; every non-banned citizen gets an `offer` notification. `POST /api/offers/claim` runs under `BEGIN IMMEDIATE`, re-checks `remaining > 0`, inserts the claim, decrements `remaining`, creates a new galaxy with the claimer as commander, adds membership, and notifies the claimer and the publisher — so “抢夺” is first-come-first-served and cannot be double-claimed. The publisher or developer can cancel with `POST /api/offers/cancel`.
- **Notifications** (`messages`): written by role changes, bans, review decisions, offer publication/claims, commander appointments/revocations, and kicks. `GET /api/messages` + `POST /api/messages/read` back 个人中心 → 新消息; `unread` is also included in `/api/auth/me`.
- **Reviewer / system listing**: `/api/admin/systems` (`developer`/`admin`) returns every system including rejected ones. Public `/api/list-galaxies` takes the viewer from the session cookie so owners still see their own rejected posts; `status`, `reviewNote`, owner `id`/name, and `submittedAt` are part of the record.

**Frontend modules**

- [js/session.js](js/session.js) — the only session/API helper: `apiPost` (JSON, `credentials:'same-origin'`), `refreshSession`, `login`/`register`/`logout`, `onSessionChange`, and derived permission helpers (`isStaff`, `isDeveloper`, `getMembershipIds`, `getCommandedGalaxies`, `canEditGalaxy`, `canManageGalaxyMembers`, `roleLabel`, `roleIcon`, `escapeHtml`). `apiPost` clears the local user on HTTP 401. **User ids are opaque TEXT** (`u_<hex>`) — never `Number()` them.
- [js/activity.js](js/activity.js) — "what the user has already seen" helper behind every red dot / 新 tag. Seen timestamps are stored per user+scope in `localStorage` under `universe_activity_seen_v1` (no DB schema change). `getSeenAt` / `markSeenAt` (only ever advances) / `markSeenFromItems(userId, scope, items, pick)` / `isNewSince(seenAt, ts)`, plus the two helpers callers should use — `ensureSeenAt(userId, scope, items, pick)` (initializes the baseline to the newest item's timestamp, so pre-existing history is never flagged as new) and `scopeHasNew(userId, scope, items, pick)`. Callers additionally keep the new ids in a session `Set` so a row's 新 tag stays visible after the dot clears.
- [js/PersonalCenter.js](js/PersonalCenter.js) — 个人中心 overlay (z-index 1300), opened by the top-right 🧑‍🚀 button or a login gate. Logged-out state shows login/register; logged-in is a **sidebar layout** (`.pc-layout` → `.pc-sidebar` + `.pc-content`): the left sidebar holds the user card, `.pc-nav` tabs (我的系统 / 消息与资格 / 账号设置, with unread/draft counts) and 退出登录, and the panel is re-rendered from `_tab`. 我的系统 merges every system the user created (review status, draft 完成发布, edit entry) with commander/membership info. Refreshing no longer auto-reads messages: `_collectNewItems()` compares 消息 / 资格 / 我的系统 against the `activity.js` markers, draws `.pc-nav-dot` on tabs that have unseen items plus `.pc-new-tag` on those rows, and `_markTabSeen(tab)` marks only the tab actually being viewed (for messages it then calls `/api/messages/read` and `refreshSession(true)`). Registration ends in a blocking `.pc-credential-modal` (请牢记你的账号密码 + the just-entered 账号/密码 + 确认登录): the overlay refuses to close until 确认登录, then the real login state is refreshed. It exposes `openLogin()`. On ≤820 px the sidebar becomes a horizontal top nav (handled in `css/community.css`).
- [js/AdminPanel.js](js/AdminPanel.js) — the **single management window** for staff and commanders. Staff see 网站管理 with header 添加星系 (发布星系资格 / 直接添加星系) and tabs 用户 / 内容管理 / 星系管理 / 星系资格 / 背景音乐 (developer only). A citizen who commands galaxies opens the same component in **commander mode** via `openCommander()`: title 🛰 星系管理, only the 星系管理 tab, filtered to their `commandedGalaxies`, with no add menu. The 用户 and 星系管理 tabs each have a client-side search box (`.ap-search-input`, `#ap-user-search` / `#ap-galaxy-search`) that filters rows by their lower-cased `data-search` text and shows an empty-state when nothing matches — it never hits the server. `openGalaxyManage(galaxyId)` opens the ⚙ 编辑信息 / 成员 modal (galaxy info + SVG icon + member list with kick) inside the panel; `AdminPanel` owns this UI, so there is no separate GalaxyManager module. Admins can delete systems but the 编辑 action is developer-only; user role changes, account deletion, galaxy deletion, review, and BGM upload are developer-only. **Commander appointment/revocation lives only in the 用户 tab** (per-user 星系指挥官 selector + 👑 tags with ✕), not in 星系管理. 星系管理's 删除星系 must call `deleteUniverseGalaxy()` from `UniverseRegistry` (it also purges the `localStorage` cache) — calling `/api/delete-universe-galaxy` directly lets `loadUniverseGalaxies()` re-upload the deleted galaxy on the next load. BGM upload/delete calls `onBgmChanged` so the in-app player refreshes. The tab's 🎵 打开播放器 button calls `onOpenBgmPlayer`, wired to `BGMManager.openPopup()` — **this is now the only entry to the music player**; the old top-right `#bgm-control` button was removed as redundant with 背景音乐 (`openPopup()` raises `#music-popup` to z-index 1500 so it sits above the admin overlay at 1300). Tabs carry `.ap-tab-count` (pending reviews on 内容管理) and `.ap-tab-dot` while `_tabHasNew(tab)`; rows carry `.ap-new-tag` 新 from `_collectNewItems()` (scopes `admin:users` / `admin:systems` / `admin:galaxies` / `admin:offers`), and the 星系管理 rows / galaxy modal members carry 新成员 / 新 from the per-galaxy `galaxy-members:<id>` scope (`_loadMembers()` snapshots new member ids before marking them seen). The module exports `computeEntryActivity()` — for staff it answers "is anything pending review?", for commanders "did anyone join a galaxy I command?" — used by the top-right entry dot.
- [css/community.css](css/community.css) — all `.pc-*` / `.ap-*` / `.gm-*` styles plus top-right entry positioning: `#site-admin-btn` sits immediately left of 星体数据库 at `right: 344px`, `#profile-btn` occupies the far-right slot where the removed BGM button used to be, and every button to its left uses `right: calc(Npx - var(--toolbar-shift))`. `body` sets `--toolbar-shift: 54px` and `body.has-admin-entry` resets it to `0`, so when a role has no 🛠/🛰 entry the remaining buttons slide right and stay on one contiguous row. It also styles the activity markers (`.pc-nav-dot`, `.ap-tab-dot`, `.pc-new-tag` / `.ap-new-tag`, `.entry-dot`) and the registration `.pc-credential-modal`, and defines the `.hidden` rule for these buttons, which the global stylesheet does not provide.
- `main.js` `_setupCommunity()` constructs the two overlays and wires the buttons (`#profile-btn` → personal center, `#site-admin-btn` → `AdminPanel.open()` for staff or `openCommander()` for commanders); `_updateCommunityEntries()` toggles the shared 🛠/🛰 entry, the `body.has-admin-entry` class and the unread badge on every session change, then `_refreshEntryDot()` paints `#site-admin-dot` from `computeEntryActivity()` (also re-polled every 60 s while the tab is visible); `_refreshCommunityWorld()` re-syncs 星体数据库 / 宇宙视图 after review, deletion, or galaxy changes.

**Star-system browser and universe view integration**

- 星体数据库 lists all systems (search only; no 全部 / 我的系统 tabs, since the personal center owns 我的系统). Each card shows its 所属星系, owner, and review status; 审核中 cards are public, 驳回 cards are dimmed with the review note. Edit is allowed for the developer or the owner (admins may only delete); the add form requires login and, for citizens, membership in the target galaxy. The **🔗 编辑星体关联** entry lives inside the add/edit compiler (`#ag-relations-btn`): editing a saved system opens its relations, while a new unsaved system asks the user to save first.
- 宇宙视图 (`UniverseView.setViewer`) hides 星系编辑 from non-developers, gates 添加星系 / join / edit / manage by role and membership, and routes 编辑星系 to its own galaxy editor and ⚙ 编辑信息 / 成员 to `AdminPanel.openGalaxyManage`. The **＋ 添加星体系统** button is always visible, even with every galaxy collapsed; it targets the active/previewed expanded galaxy when there is one, otherwise opens the compiler with the 所属星系 selector. The system preview shows join/leave only where permitted — the **⛓ 编辑关联 entry is not in the universe view**; body relations are edited only from the star-system add/edit compiler (`#ag-relations-btn`). New systems are created from the universe view, existing ones are edited from 个人中心 → 我的系统, and a developer can click a system card in 星体数据库 to open the compiler directly.

### Feature modules

- [js/ui.js](js/ui.js) — raycast clicks, info card, detail modal, probe launch/recall, TTS trigger. The detail modal's 关联星体 section lists the body's 主动/被动 relations as `星系 / 星体系统 / 星体`, and clicking a body name switches to its system and focuses it; `main.js` supplies the current system id and navigation through `ui.setRelationContext(...)`.
- [js/FocusController.js](js/FocusController.js) — camera tracking of a focused body and galaxy navigation. `controls.target` is kept on the body's **current** mesh position every frame and again in `dismiss()`, so leaving focus resumes orbit/pan/zoom around the planet instead of a stale empty point.
- [js/FreeFlyController.js](js/FreeFlyController.js) — 🛸 free-flight preview for star-system browsing (Outer Wilds-style): pointer-lock mouse look, WASD move, Shift boost, Ctrl/Space vertical, wheel adjusts base speed, Esc exits. The toggle button `#free-fly-btn` sits immediately left of 重绘轨道线 in the top-right toolbar (`right: 560px` in `community.css`). `main.js` calls `update(dt)` instead of `focusController.update()` while active and passes `skipControls` to `SceneManager.render`; entering exits focus, and switching systems / entering the ship calls `freeFly.disable()` first. `disable()` restores OrbitControls with the target placed in front of the camera at the previous orbit distance.
- [js/GalaxyBrowser.js](js/GalaxyBrowser.js) — exposed in the UI as **星体数据库**: list/search/edit/delete/export/import of all systems plus custom-system instantiation. It is **galaxy-first**: with an empty search and `_dbGalaxyId === null` it renders `.gb-galaxy-tile` cards (galaxy SVG icon, name, system count, commander) via `_renderGalaxyTiles`; clicking a tile sets `_dbGalaxyId` and `_renderList` calls `_renderSystemCards` for that galaxy with a `.gb-db-nav` breadcrumb (“← 星系列表”). A non-empty search always lists matching systems across every galaxy. `show()` resets to the galaxy list. Each system card still shows its parent galaxy, owner, and review status, and the add/edit compiler is opened by clicking a card (owner/developer) or the ✎ button. It owns the owner + review-status badges, the add/edit compiler (including the relation-editor entry), and the permission gates described under Community platform. The database overlay has no universe-view button of its own — the universe view is entered from the main UI's universe button.
- [js/UniverseView.js](js/UniverseView.js) — full-screen **宇宙视图** overlay: galaxy icons and the expanded star-system spheres share one scene (clicking a galaxy flashes its icon away and reveals its systems in place). Galaxies are SVG-icon sprites on a Fibonacci-sphere layout; systems are textured/colored spheres on a golden-angle disc, all with `CSS2DObject` labels. Relation lines are shown on hover and pinned on click: cyan = 主动 (`from → to`), orange = 被动 (`to ← from`). Clicking a node pins it and immediately finalizes any line growth still playing (`_finalizeLinks`); later hovers reuse the already-grown lines (static, no growth/flare replay); clicking empty canvas unpins. The pinned star system gets a four-arc selection ring sprite (`_makeSelectionRingTexture`, sized in screen pixels so it always wraps the sphere) that rotates slowly and flares its glow while hovered. OrbitControls use left-drag = rotate, middle/right-drag = pan (the main scene instead uses left-drag = pan). The top-right **星系编辑** menu splits into 添加星系 / 编辑星系; the editor lists every universe galaxy with a delete button (the default one is locked 🔒) and opens the same add/edit form prefilled through `_openEditGalaxy`. Deletion goes through `deleteUniverseGalaxy()` and then reloads `loadUniverseGalaxies()`. It owns its own renderer/scene, hides itself when a system is entered and calls `onEnterSystem(id)`, which `GalaxyBrowser` forwards to the main app's navigation callback.
- [js/UniverseRegistry.js](js/UniverseRegistry.js) — data layer for universe-level galaxies (distinct from star systems): the default `银河系` plus user-created ones, persisted to SQLite through the server and cached in `localStorage` (`universe_galaxies`) as offline fallback. Records carry the community fields `commanderUserId` / `commanderName`, `isMember`, `isDefault`. Offline-created galaxies/relations are pushed back to the DB on the next load. Systems without a `universe.galaxyId` fall back to `milky-way`; galaxy-to-galaxy links are derived from body-level relations that cross galaxy boundaries. `getSystemGalaxyId()` prefers the DB column `universeGalaxyId` over `data_json.universe.galaxyId`, and `resolveSystemGalaxyId(system, galaxies)` additionally falls back to the default galaxy when the referenced galaxy no longer exists — always use the latter when grouping systems by galaxy. `deleteUniverseGalaxy(id)` deletes on the server **and** removes the entry from the local cache.
- [js/BodyRelationEditor.js](js/BodyRelationEditor.js) — 星体关联编辑器, opened only from **🔗 编辑星体关联** in the add/edit star-system compiler (new and existing systems); system cards and the universe view no longer carry the entry. Relations are **directional**: `from → to` is the `from` system's 主动关联 and simultaneously the `to` system's 被动关联, so the editor shows separate 主动/被动 lists for the current system. The **主动方 system select is locked** to the system the editor was opened from (falling back to the active main-scene system); only the passive side can be switched. For an unsaved new system GalaxyBrowser passes a synthetic `draftSystem` (`id = '__draft_system__'`, keys `__draft_system___star` / `__draft_system___planet_<i>`); new relations stay in `_pendingRelations` with a 待保存 badge and are remapped to the real id/keys by `_commitDraftRelations()` when the system is saved. Saved drafts pass a real-id `draftSystem` marked `isDraft` so their new relations are staged the same way. Persisted to SQLite via `/api/save-body-relations` plus `localStorage` (`universe_body_relations`).
- [js/toast.js](js/toast.js) — `showToast(message, 'success'|'error'|'info')` renders the top-center `.app-toast` (z-index 12000, above every modal). Used by the detail/surface compiler save button and the prompt save button in 星语设置.
- [js/GalaxyPreview.js](js/GalaxyPreview.js) — live 3D preview beside the "create single-star system" form; owns its own renderer/scene and rebuilds whenever form values or planet rows change.
- [js/DetailTreeEditor.js](js/DetailTreeEditor.js) — folder-tree detail compiler for stars/planets/moons. The tree is stored as `detailTree` on body data (`{type:'folder'|'text'|'image', name, url?, children?}`); `.txt`/`.png`/`.jpg` files are persisted under `detail_files/` through `POST /api/upload-detail-file` and referenced by URL. `ui.js` renders the same tree in the detail modal, falling back to wrapping legacy `details` strings. The same editor has a `mode:'surface'` variant that keeps a single renameable folder of images only (≤10 MB each), stored as `surfaceTree` and rendered by `main.js` as a thumbnail grid in `#surface-overlay`.
- [add-planet/](add-planet/) — `BodyEditor` + `PlacementController`/`PlacementHUD`/`PlacementGuides` implement the 4-step placement flow; `PlanetLab` is an isolated Three.js scene that reuses `BodyEditor`. The lab header hosts AI 建造 (`LabAI`, no icon) and 🗑 擦除 (`_clearTrails`). The header wraps on narrow windows and publishes its height as `--pl-header-h` (ResizeObserver) so `.pl-sidebar` always starts below it instead of covering the header buttons. **导入星体系统** (`#pl-import-btn` → `_openImportModal`) is a searchable picker of the star-system database: each `.pl-import-item` shows the system plus `🛰 所属星系：<galaxy>` (resolved through `loadUniverseGalaxies()` + `resolveSystemGalaxyId`), `#pl-import-search` filters on system *and* galaxy name, drafts are excluded, systems without planets are disabled, and clicking a row instantiates its bodies into the lab (confirming first if the lab already has bodies). **导出星体数据库** (`#pl-export-btn` → `_openExportModal`) lists the galaxies the user belongs to or commands; picking one and pressing 保存至草稿箱 (`_saveDraftToGalaxy`) calls `onExportSystem({ ..., galaxyId, draft: true })`, i.e. the system is created as a private draft and the user is told to finish it in 个人中心 → 我的系统. Both flows require a logged-in user and fall back to `onRequireLogin`.
- [add-planet/Blueprint.js](add-planet/Blueprint.js) — declarative lab-system spec: `normalizeBlueprint(raw)` clamps/validates an AI JSON blueprint, `computeAssembly(blueprint)` turns it into SI positions/velocities (modes `planetary` / `binary` / `triple` / `figure8` / `free`, ≤16 bodies), and `describeAssembly` summarizes it. AI never emits code, only this JSON.
- [add-planet/LabAI.js](add-planet/LabAI.js) — 实验室 AI dialog (`.pl-ai-modal`, topmost in `planetLab.overlay`). Calls `chatOnce` with `buildLabBuilderPrompt`, parses + repairs the JSON once, then hands the assembly to `PlanetLab.applyBlueprint(assembly)`, which clears the lab, disables collision mode, creates `CelestialBody` instances, fits the camera, and sets a time scale via `_autoTimeScale`. The panel has no title bar text/icon — just a drag grip, a ✕, and a bottom-right resize handle; it is a very translucent Claude-orange frosted-glass panel (`rgba(58,35,27,.34) → rgba(24,16,13,.18)` + `backdrop-filter: blur(24px)`); the circular ✕ sits inside the 30 px drag bar with a 3 px gap above its bottom border. Drag/resize state is tracked with `window`-level `pointermove`/`pointerup` listeners, not `setPointerCapture`.
- [add-planet/InfiniteGrid.js](add-planet/InfiniteGrid.js) — shader-based infinite grid used by the lab. Lines are computed from world-space XZ coordinates on a large plane that follows the camera horizontally, so they stay fixed in space and stream toward the horizon (Minecraft-style). `update(camera, target)` refreshes the plane position, camera uniform, and distance fade each frame; the Y axis is a long green `Line`. `PlacementGuides.disableGrid()` removes the old finite `GridHelper`/axes so the placement flow does not re-add them.
- [ship/js/](ship/js/) — `ShipModule` is a state machine (`universe` → `entering` → `ship` → `exiting`), uses `PointerLockControls`; the main animation loop delegates update/render to it while active.
- [model-chat/js/](model-chat/js/) — the **星语终端** overlay. See the AI subsystem section below.
- [js/voice_settings.js](js/voice_settings.js) — in-app TTS via the browser `SpeechSynthesis` API. [voice_handle/voice.py](voice_handle/voice.py) is a **separate offline DSP synthesizer** (numpy/pyttsx3/scipy/sounddevice) and is not called by the web app.
- [js/SoundManager.js](js/SoundManager.js) exports a singleton and also sets `window.__soundManager`; the non-module [js/fuiButtons.js](js/fuiButtons.js) depends on that global.

### AI subsystem (星语终端 + 实验室 AI)

- **Entry points**: `main.js` binds `#chat-launcher` directly to `openOverlay()` — there is no login gate. The conversation window closes **only** through its top-right ✕ (`#chat-close-btn2`); there is no outside-click handler.
- [model-chat/js/config.js](model-chat/js/config.js) merges config sources in this precedence: `localStorage` (`stellar_ai_config`) > `model-chat/key.json` (gitignored; `key-up.json` is the committed template) > defaults. Two modes: `api` (cloud key + base URL + model) and `local` (local OpenAI-compatible server URL, optional key/model). The 🔐 API key is stored **only** in the browser's localStorage and must never be put into prompts, messages, logs, or committed files.
- [js/voice_settings.js](js/voice_settings.js) renders the settings page: 📢 语音 on the left and, under 提示词, a two-column `.vs-ai-layout` whose left column is the AI API/local config (`vs-ai-*` fields) and whose right column is `#vs-prompt-input`.
- [model-chat/js/api.js](model-chat/js/api.js) — OpenAI-compatible chat completions: `chatStream` (SSE) for the terminal and `chatOnce` for the planner/lab (non-streaming). `config.js`/`api.js` are shared by the terminal and the lab.
- [model-chat/js/agent.js](model-chat/js/agent.js) + [model-chat/js/prompts.js](model-chat/js/prompts.js) — fixed identity/system prompts; `buildLabBuilderPrompt(schemaDoc)` is the lab prompt.
- **Two-phase sandbox** in [model-chat/js/context.js](model-chat/js/context.js): phase 1 makes the model return `{systems:[], galaxies:[], relations, reason}`; the program validates every id against the catalog, discards unknown ids, then reads only those records via `getSystemInterface` / `getGalaxyInterface`. The model has no DOM/localStorage/network access and never executes generated code. Hard caps: `MAX_SYSTEMS=8`, `MAX_GALAXIES=6`, `MAX_CONTEXT_CHARS=14000`, `MAX_DETAIL_FETCHES=10` (only `/detail_files/` URLs, 4s abort).
- Built-in moons are not in `getAllGalaxies()`; `context.js` supplements them through the explicit `BUILTIN_MOONS` map. Only the solar-system module exports `MOON_CLASSES` — do not import moon classes from other built-in systems.

### Python server

[server.py](server.py) uses only the Python standard library (+ [db.py](db.py)) and listens on port 8000:

- `GET /` → `index_font/heidong.html`; all other static files served from the repo root.
- `GET /detail_files/<name>` — text from the DB, images from their relative path.
- `POST /api/list-galaxies` — list `systems` rows with `kind='custom'`; each record includes `star`/`planets` and relative `texturePath`s.
- `POST /api/create-galaxy` — insert a new custom system in the DB, materialize images under `Galaxy/custom/<id>/media/`, and write the `index.js` stub. Returns `{ok, id, galaxy}` (the normalized record).
- `POST /api/update-galaxy` — overwrite an existing record in place (keeps `id`/folder and `createdAt`). Both create/update accept `draft: true` (`status='draft'`).
- `POST /api/publish-system` — flip an owner's draft to `pending` (citizen, re-checks galaxy membership) or `approved` (developer); admins cannot publish systems.
- `POST /api/delete-galaxy` — delete the DB row and remove the custom folder.
- `POST /api/export-galaxies` — zip selected folders into `output/`, regenerating `data.json` from the DB record.
- `POST /api/upload-detail-file` — `.txt` content goes into the DB; `.png`/`.jpg` (`dataUrl`) is written to `detail_files/` with only `rel_path` stored; returns `{ok, filename, url}`.
- `POST /api/import-galaxy` — raw zip body (not JSON), extracted into `Galaxy/custom/` (zip-slip guarded), normalized into the DB, images materialized into the imported folder.
- `POST /api/list-universe-galaxies` / `save-universe-galaxy` / `delete-universe-galaxy` — CRUD in the `universe_galaxies` table (`icon_svg` text); the default `milky-way` record cannot be deleted. Create/edit requires the developer or that galaxy's commander; `commanderUserId` is honored only from a developer.
- `POST /api/list-body-relations` / `save-body-relations` — read / replace the whole relation list in `body_relations` (requires login).
- `POST /api/migrate-local-data` — merge browser `localStorage` payloads (`{systems, universes, relations}`) into the DB; existing newer rows win.
- **Auth**: `POST /api/auth/register` / `login` / `logout`, `GET /api/auth/me`, `POST /api/auth/profile` (display name / password). Login/register set the session cookie; `_need_user` returns 401 when absent.
- **Community reads/writes**: `POST /api/my-systems`, `/api/my-memberships`, `/api/galaxy/join|leave|members|kick`, `/api/offers/list|publish|claim|cancel`, `/api/messages`, `/api/messages/read`, `/api/review-system`, `/api/admin/systems|users|set-role|set-banned|delete-user|set-commander`.
- **Developer-only BGM**: `/api/admin/list-bgm|upload-bgm|delete-bgm` edit `music/index.json` plus audio files (name validated by `_safe_audio_name`); the client caches the music index in `localStorage`.
- Role guards are `_need_user` / `_need_staff` (developer or admin) / `_need_developer`; every community mutation re-checks ownership/role in `db.py`, not just in the handler.

`start.py` kills whatever is listening on port 8000 (Windows `netstat`/`taskkill`), then launches `server.py`. Port references to **8765** in `ADDXINGXI.md` / `Galaxy-模块标准模板.md` are stale; the running server is on **8000**.

## Conventions and gotchas

- Keep relative import paths with the `.js` extension — there is no resolver or bundler.
- Cache busting is manual via query strings: `js/main.js?v=...`, `css/style.css?v=...`, `css/community.css?v=...`, `ship/css/ship.css?v=...` in `index.html`, plus per-import `?v=` suffixes in `main.js` and other modules (e.g. `GalaxyBrowser.js?v=38`, `UniverseView.js?v=27`, `AdminPanel.js?v=10`, `PersonalCenter.js?v=8`, `PlanetLab.js?v=13`, `activity.js?v=2`, `BodyRelationEditor.js?v=5`, `bgm.js?v=4`, `galaxyRegistry.js?v=8`, `UniverseRegistry.js?v=7`, `session.js?v=1`). Bump the relevant one when changing that entry module/style if an old cached copy causes confusion.
- SQLite (`Galaxy/universe.db`) is the source of truth for text data. Do not add new writes to `Galaxy/universes.json` / `Galaxy/body_relations.json` / `Galaxy/custom/*/data.json`; those files are legacy backups only (export still generates `data.json` inside the zip).
- Never store image bytes/data URLs in the DB. Save the file under `Galaxy/custom/<id>/media/` (or `detail_files/`) and persist only the repository-relative path text; `_toTexturePath` must pass relative paths through instead of base64-decoding them.
- `/api/save-body-relations` **replaces the entire table**, so callers must send the complete merged list (as `UniverseRegistry._persistBodyRelations` does).
- The most common unit bug is mixing SI meters (`ORBIT_RADIUS`, physics positions) with scene units (`MoonBody.ORBIT_RADIUS`, `VISUAL_RADIUS`, mesh coordinates). Convert deliberately.
- OrbitControls must never get `minDistance = 0` (main scene and PlanetLab use 0.5). With the camera collapsed onto the target, rotation is imperceptible, pan speed (proportional to distance) approaches zero, and zooming back out needs hundreds of wheel ticks. Keep `controls.target` synced to the focused body's current mesh position when leaving focus, and leave `zoomToCursor = true` so close-up navigation stays usable. `enableDamping = true` + `dampingFactor = 0.08` gives the drag/pan/zoom inertia; because damping needs `controls.update()` every frame, `SceneManager.render` must keep calling it (skipped while `FreeFlyController` is active).
- Custom icon images (`<img>`-style URLs, notably the `.svg` galaxy icons) must be drawn onto a `<canvas>` and uploaded as a `CanvasTexture`; mapping the loaded SVG image directly as a sprite texture renders as fully transparent in some WebGL implementations (including headless Chromium).
- When removing bodies, dispose geometries/materials and remove them from both the scene/group and `PhysicsEngine` (see `GalaxyBrowser._deleteGalaxyBodies` and `CelestialBody.dispose`). The same applies to `CSS2DObject` labels: removing a group from the scene without calling its `_destroyGroup`-style disposer leaves the HTML labels on screen, because `CSS2DRenderer` only cleans up objects it still tracks.
- `model-chat/key.json` holds API credentials and must never be committed; `.gitignore` already excludes it.
- A module imported with different `?v=` suffixes is instantiated **twice**. This matters most for the AI modules: `model-chat/js/config.js`, `api.js`, `prompts.js`, `context.js`, `agent.js`, and `add-planet/Blueprint.js` must be imported with the same version everywhere (terminal, settings, lab).
- Lab AI builds deliberately turn **collision mode off** and derive the time-scale slider from the assembly's median orbit period — large visual radii otherwise produce enormous rigid spheres that fling bodies apart. `applyBlueprint` also asks for confirmation before clearing existing lab bodies.
- The chat header drag handler calls `setPointerCapture` on `pointerdown`; Chrome then retargets the subsequent `click` to the header, so any button inside it must stop `pointerdown` propagation (the ✕ close button does exactly this). Keep that guard if you add more header buttons.
- Do not rely on element-level `setPointerCapture` for drag handles: once the pointer leaves a small handle (the AI dialog's 20 px resize corner), capture can fail and later events land on the backdrop, freezing the drag. The AI dialog therefore listens for `pointermove`/`pointerup` on `window` and removes those listeners on release.
- The 星语终端 chat has **no read-aloud UI** (`.msg-speak-btn` and auto-speak were removed). Browser TTS remains only for body introductions via `js/voice_settings.js` / `vsSpeak`.
- When adding a built-in system that exports `MOON_CLASSES`, register it in `BUILTIN_MOONS` in `context.js` so the AI can see its moons.
- Browser `AudioContext` and TTS require a user gesture; `SoundManager.init()` preloads buffers but playback only works after interaction.
- `server.py` is a local dev server: it binds `0.0.0.0:8000` and serves **all static files without authentication** (the community session only protects `/api/*`). It also has no TLS. Do not expose it on an untrusted network; a real deployment needs HTTPS, a reverse proxy, and static-file gating.
- **User ids are opaque TEXT** (`u_<hex>`). `Number(id)` produces `NaN` and breaks role/commander/kick calls — pass the string through (`AdminPanel.js` previously had this bug).
- Authorization must stay server-side. `_need_staff` / `_need_developer` and the ownership checks in `db.py` are the boundary; `session.js` helpers only drive UI visibility.
- Never seed or assume a developer account. The **first registration** becomes developer and takes over legacy ownerless systems; deleting that account would leave the site without a developer, which is why `delete_user` refuses developer targets.
- Review visibility: `pending` is public, `rejected` is owner/staff only, and `draft` is owner-only (never public, never instantiated in the scene). `list_systems` needs the viewer (from the session), so callers must not fetch it with a hard-coded anonymous viewer.
- `/api/save-body-relations` replaces the whole table, so the server re-adds relations that touch another user's drafts; otherwise a single save by anyone would delete a draft's staged relations.
- `galaxy_offers` claiming must stay inside `BEGIN IMMEDIATE` with a re-read of `remaining`; the `offer_claims` primary key alone is not enough to prevent a lost update.
- Community modules import `session.js`/`toast.js`/`UniverseRegistry.js` with explicit `?v=` suffixes; bump them consistently everywhere or the browser instantiates duplicate session state (one copy sees the login, another does not).
- `css/community.css` provides the `.hidden` rule for `#site-admin-btn`; the global stylesheet has no generic `.hidden`, so removing that rule makes the staff-only entry permanently visible. Whenever the entry is hidden, `body.has-admin-entry` must be removed in the same breath (`_updateCommunityEntries`) — that class drives `--toolbar-shift`, and without it the toolbar keeps a 54 px hole instead of sliding the remaining buttons together.
- Red dots must come from the `activity.js` markers, never from a one-off boolean: the marker is what makes the dot clear only after the user actually sees the list, and it must be initialized from existing item timestamps so a first visit does not flag all history. Row 新 tags come from the session id `Set`, so they may outlive the dot.
- `#site-admin-btn` is shared: staff get full 网站管理, commanders get the same `AdminPanel` in commander mode (星系管理 only). Do not add a second top-right galaxy-manager button, and keep the commander list filtered by `commanderUserId === user.id` — `_renderGalaxies` and `openGalaxyManage` rely on that filtering.
- After review/delete/galaxy changes, call `main._refreshCommunityWorld()` (or `GalaxyBrowser.refreshCommunity()`) instead of reloading the page, and `refreshSession(true)` after any change that affects role/command/unread state.
- **Never delete a universe galaxy with a raw `apiPost('/api/delete-universe-galaxy')`.** `loadUniverseGalaxies()` treats `localStorage` entries missing from the server as offline-created and re-uploads them, so the galaxy reappears after a refresh. Always call `UniverseRegistry.deleteUniverseGalaxy(id)`, which clears the local cache; `db.delete_universe_galaxy` additionally reassigns its systems to `milky-way` in both `universe_galaxy_id` and `data_json.universe.galaxyId` and drops its `galaxy_members` rows.
